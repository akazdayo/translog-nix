# Nix バイナリキャッシュの配布透明性設計

## 目的

Nix の input-addressed な store path は、通常、ビルド出力の内容そのものを表すアドレスではない。同じ store path に対してキャッシュが後から異なる NAR を配布する場合、過去と同じ内容を取得できるとは限らない。

本システムは、既存のバイナリキャッシュが配布する NarInfo を外部から観測し、検証可能な履歴として保持する。最初に記録した NarInfo を基準として利用者に返し、その基準に合う NAR を取得できるか Nix の既存の検証機構を使って確認する。上流を再観測し、基準との変化も記録・通知する。

ここでいう「キャッシュの再現性」は、**あるキャッシュの同じ store path に対して、基準として記録したものと同じ内容を取得できること**を指す。NAR を保存する設計ではないため、上流がその内容を削除した場合の取得可能性は保証しない。

## 対象としないこと

- ビルドが決定論的か、複数回のビルド結果が一致するかの判定。
- 異なる NAR のどちらが正しいか、変化が不正か正当かの判定。
- 複数 substituter やフォールバックの扱い。
- 初回観測以前の配布履歴や、観測者が見ていない特定利用者向けの配布の網羅。
- NAR 本体の保存や、上流で削除された NAR の提供保証。

## 構成

```text
                      観測・再観測
上流キャッシュ ─────────────────────→ ログサーバー
      │                              │  履歴・基準を保持
      │                              │  metrics を公開
      │                              ↓
      │                       ローカル / セルフホスト
      │                           プロキシ
      │                              │
      │                       基準 NarInfo
      │                              ↓
      └──────── NAR の取得 ────────→ Nix
                            署名とハッシュを検証
```

- **ログサーバー**: 上流の NarInfo を観測し、履歴と初回の基準を保持する。基準をプロキシに提供し、Prometheus metrics を公開する。
- **プロキシ**: ログサーバーから基準 NarInfo を取得し、Nix の substituter として返す。利用者の PC または任意のサーバー上でセルフホストできるよう、オープンソースで提供する。
- **Nix**: 元の署名を検証し、NarInfo が示す NAR を取得して内容と `NarHash` の一致を検証する。

NarInfo と NAR の配信経路に関する先行実験として [repro2](https://github.com/akazdayo/repro2) を参照する。

## 基準の作成と配信

基準は、対象キャッシュの識別子と完全な store path の組ごとに保持する。キャッシュの識別子とエンドポイントを記録するが、識別子の具体的な形式や URL の変更・ミラーとの関係は未決定とする。

1. Nix がプロキシに store path の NarInfo を要求する。
2. 基準が未登録の場合、プロキシはログサーバーに取得を依頼する。
3. ログサーバーは上流から NarInfo を取得し、要求対象の store path に対応することと、設定された信頼済み公開鍵による署名を検証する。
4. 検証に成功した観測を履歴に記録し、その組の初回の有効な記録を基準として固定する。検証に失敗したものは基準にしない。
5. プロキシは基準 NarInfo を Nix に返す。NAR は上流から取得する。
6. Nix は通常の署名検証と NAR の内容検証を行う。

同じ組の初回要求が同時に到着しても、採用する基準は一つとする。基準の確定と履歴への記録は、競合や障害によって食い違わないように扱う。ここでの初回とは、上流で最初に配布された時点ではなく、**本システムが有効な観測を初めて記録した時点**である。

基準に記録された `StorePath`、`NarHash`、`NarSize`、`References` と元の署名を維持する。Nix の署名対象にはこれらが含まれるが、NAR の `URL` は含まれない。NAR の取得先を上流に向けるための処理は署名対象を変えずに行う。署名の検証と、実際の配布元 URL・時刻の証明は別である。

初回の取得、署名検証、ログへの記録に失敗した場合、未記録の NarInfo を基準として返さない。エラーの詳細な API 表現や再試行方法は実装時に決める。

## 再観測と変化の扱い

登録済みの対象をバックグラウンドで再観測する。再観測は基準 NarInfo を返す処理とは分け、上流への問い合わせを基準の配信に同期させない。

- 同じキャッシュ・store path に対して、基準と異なる `NarHash` を観測したら、変化として履歴に記録し、metrics で通知する。
- 基準は自動更新しない。異なるハッシュの観測は、ビルドの非決定性、運用変更、攻撃などの原因や正当性を判定するものではない。
- 基準の NarInfo を返した際に、指定された NAR が異なる内容になっていれば、Nix の検証で不一致となる。古い NAR が削除されていれば取得に失敗する。
- 上流が新しい NarInfo と NAR を提供しつつ古い NAR も残している場合、基準を使った取得は成功しうる。新しい NarInfo への変化は上流の再観測によって検出する。

再観測の間隔、スケジューリング、重複した変化の記録方法、上流エラー時の再試行方法は未決定とする。再観測は、観測の間にだけ存在した状態や観測者に見えない応答を保証して検出するものではない。

## 履歴と信頼境界

履歴には、少なくとも対象キャッシュの識別子とエンドポイント、store path、観測した NarInfo、観測時刻、検証結果、および基準との関係を保持する。署名を後から検証できるよう、元の NarInfo を保持する。観測時刻は観測者の申告であり、ログへの記録順序とは区別する。

履歴は追加のみを基本とし、外部から読んで監査できる形で保持する。署名付きチェックポイント、Merkle tree、包含証明や整合性証明を含む具体的なログ形式・検証プロトコルは今後決定する。単に公開された履歴や metrics があるだけで、改変や利用者ごとに異なる履歴の提示を暗号学的に防止・検出できるとは扱わない。

初期設計では、基準の検索と配信に関してログサーバーおよび利用するプロキシを信頼する。ソフトウェアを公開しセルフホスト可能にすることで、利用者自身による運用と検査を可能にする。Nix の元のキャッシュ署名の検証は引き続き必要であり、プロキシ用の署名鍵は必要としない。

元の署名は署名対象の store object に関する主張を検証するが、指定 URL が特定の時刻に NarInfo を返したことまでは証明しない。ログの観測は観測者が見たという主張であり、初回観測時点ですでに内容が変わっていた場合も、本システムだけではそれを判断できない。

## 監視

ログサーバーは Prometheus metrics を公開する。Prometheus / Alertmanager などで、少なくとも次の状態を監視できるようにする。

- 初回観測して基準を固定した対象の数。
- 基準と異なる `NarHash` を観測した回数。
- 上流への問い合わせ、署名検証、ログ記録などのエラー。
- 再観測の待機状況と成功状況。

metrics の名前、型、カウント方法やラベルは未決定とする。store path ごとにラベルを作ると時系列が増大するため、metrics は集約値を中心とし、個別の変化は履歴または検索 API で確認できるようにする。

metrics はログサーバー自身の報告であり、サーバーが報告しなかった変化や履歴の隠蔽をそれだけで検証するものではない。

## 将来の拡張

- 利用者側プロキシによる、ログの署名付きチェックポイントや包含・整合性証明の検証。
- 最初の記録を検証可能に求める仕組み。包含証明だけでは、より前の記録が存在しないことは証明できない。
- 独立した monitor、チェックポイントの共有、ログの第三者監査。
- nixpkgs の特定 revision から対象の input-addressed な出力を列挙し、要求に先立って観測する仕組み。対象の列挙方法や実行コストは未検討。

## 未決定事項

- ログの具体的なデータ形式、API、証明方式、保存・復旧方法。
- キャッシュ識別子、信頼済み公開鍵の設定・ローテーション方法。
- 同一 `NarHash` で URL・圧縮・署名などの配信メタデータだけが変わった場合の記録と扱い。
- 初回固定後に正当な理由で基準の変更が必要になった場合の明示的な運用手順。
- 再観測のスケジュールと負荷、初回取得に失敗した場合の API と再試行。
- プロキシのローカル配置・公開配置それぞれの具体的な設定方法。
