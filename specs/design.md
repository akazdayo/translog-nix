# Nix バイナリキャッシュの配布透明性設計

## 目的

Nix の input-addressed な store path は、通常、ビルド出力の内容そのものを表すアドレスではない。同じ store path に対してキャッシュが後から異なる NAR を配布する場合、過去と同じ内容を取得できるとは限らない。

本システムは、既存のバイナリキャッシュが配布する NarInfo を Observer が観測し、Transparency Log に検証可能な履歴として記録する。プロキシはログをローカルに同期し、上流キャッシュの URL と store path の組ごとに、ログで最初に記録された有効な NarInfo を基準として使い続ける。Nix は基準に対応する NAR を取得し、既存の署名・内容検証を行う。

ログが未同期で対象の記録がない場合、プロキシは上流から取得した NarInfo を先に返す。そのため、初回配信の内容が、後に同期したログの基準と異なる可能性がある。この差の検出・通知は当面対象外とする。

ここでいう「キャッシュの再現性」は、**同じキャッシュの同じ store path に対して、基準として記録したものと同じ内容を取得できること**を指す。NAR 本体は保存しないため、上流が基準に対応する NAR を削除した場合の取得可能性は保証しない。

## 当面の対象外

- 基準と異なる内容の観測や、初回配信と Observer の観測の差を通知する仕組み。
- ビルドが決定論的か、複数回のビルド結果が一致するかの判定。
- 異なる NAR のどちらが正しいか、変化が不正か正当かの判定。
- 複数 substituter やフォールバックの扱い。
- 初回観測以前の配布履歴や、観測者が見ていない特定利用者向けの配布の網羅。
- NAR 本体の保存や、上流で削除された NAR の提供保証。

## 構成

```text
                            観測依頼（非同期）
                        ┌────────────────────→ Observer
                        │                          │
                        │                    上流から観測
                        │                          ↓
Nix ── NarInfo 要求 ──→ Proxy              Transparency Log
 ↑                      │                          │
 │                      ├── 上流から NarInfo 取得  │ 定期同期・検証
 │                      │                          ↓
 └── NarInfo を受取 ────┘                   ローカルのログ

Nix ──────────────── 上流から NAR を取得・検証
```

- **Observer**: 観測依頼を受け、上流から NarInfo を取得して検証し、Transparency Log に記録する。NarInfo の配信は担当しない。
- **Transparency Log**: 観測履歴を追記し、署名付きチェックポイントと検証に必要なログデータを公開する。Tessera を使う。
- **プロキシ**: Nix の substituter として NarInfo を返す。ログを定期的にローカルへ同期・検証し、同期済みの最初の記録を基準として使う。記録がない場合は上流から取得し、Observer に観測を非同期で依頼する。
- **Nix**: 元の署名を検証し、NarInfo が示す NAR を取得して内容と `NarHash` の一致を検証する。

プロキシは利用者の PC または任意のサーバー上でセルフホストできるようにする。NarInfo と NAR の配信経路に関する先行実験として [repro2](https://github.com/akazdayo/repro2) を参照する。

## 基準と配信

対象は、上流キャッシュの URL と store path の組で識別する。URL が変われば別のキャッシュとして扱う。基準となるのは、**同期・検証済みの Transparency Log において、その組について記録順で最初に現れた有効な観測**である。上流で最初に配布された時点ではない。

1. Nix がプロキシに store path の NarInfo を要求する。
2. プロキシのローカルログに対象の記録があれば、記録順で最初の有効な NarInfo を返す。基準は自動更新しない。
3. 対象の記録がなければ、プロキシは上流から NarInfo を取得して返し、Observer に観測を非同期で依頼する。ログへの記録や同期の完了は待たない。
4. Observer は独立して上流から NarInfo を取得し、要求対象との対応と信頼済み公開鍵による署名を検証する。有効な観測を Transparency Log に送る。
5. プロキシはログを定期的に同期・検証し、後の要求では同期済みの最初の記録を基準として使う。
6. Nix は NarInfo の署名と、取得した NAR の内容を検証する。

ログ同期後は同じ組の最初の有効な記録を一つの基準として使う。ログへの記録・同期前には、同時要求が異なる上流応答を受け取る可能性があり、初回配信に同一基準を保証しない。プロキシの初回取得と Observer の観測が異なる場合の処理も当面対象外とする。

基準に記録された `StorePath`、`NarHash`、`NarSize`、`References` と元の署名を維持する。Nix の署名対象にはこれらが含まれるが、NAR の `URL` は含まれない。上流への NAR 取得先の設定は署名対象を変えずに行う。上流が基準の NAR を変更または削除した場合、Nix の内容検証または取得が失敗し得る。

## ログの同期と信頼境界

Observer は上流 URL、store path、元の NarInfo、観測時刻などをログに記録する。観測時刻は Observer の申告であり、ログへの記録順序とは区別する。元の NarInfo を保持することで、その署名を後から検証できるようにする。

プロキシは Transparency Log から署名付きチェックポイントと、観測データおよび検証に必要なデータを定期的に取得し、ローカルに保持する。同期間隔は約1時間を想定する。チェックポイントの署名と、以前のチェックポイントからの追記の整合性、および取得した観測がチェックポイントに対応することを検証してから、同期済みの記録として使う。初回同期と更新時の具体的な手順、必要なデータの保存方法や索引は実装時に決める。

ログへの包含は Observer がその観測を記録したことを示すが、上流が特定の時刻にその応答を返したことや、観測者の見ていない応答が存在しなかったことは証明しない。ログの署名付きチェックポイントと整合性の検証だけでは、ログが異なる利用者に異なる履歴を提示することも単独では検出できない。独立した監視者やチェックポイントの共有は将来の拡張とする。

上流の元の署名は引き続き必要であり、プロキシ用の署名鍵は必要としない。ログのチェックポイント検証に使う公開鍵は、別途信頼できる方法で設定する。

## 将来の拡張

- 基準と異なる `NarHash` の観測や、プロキシの初回取得と Observer の観測の差の検出・通知。
- 独立した monitor、チェックポイントの共有、ログの第三者監査。
- nixpkgs の特定 revision から対象の input-addressed な出力を列挙し、要求に先立って観測する仕組み。

## 未決定事項

- Observer への依頼が失敗した場合の再送や、観測・記録が完了しない場合の扱い。
- Observer が依頼後も定期的に再観測するか、そのスケジュールと負荷。
- ログ同期・署名検証・整合性検証に失敗した場合に、既存のローカルログや未記録の対象をどう扱うか。
- ローカルログの保存・復旧・検索方法、同期間隔と初回同期の負荷。
- 同期済みログから最初の有効な観測を確実に特定するための検証・索引方法。
- 信頼済み公開鍵の設定・ローテーション方法。
- 同一 `NarHash` で URL・圧縮・署名などの配信メタデータだけが変わった場合の扱い。
- 正当な理由で基準の変更が必要になった場合の明示的な運用手順。
- プロキシのローカル配置・公開配置それぞれの具体的な設定方法。
